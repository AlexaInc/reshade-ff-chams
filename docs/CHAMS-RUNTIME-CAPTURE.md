# Chams Runtime Capture — use and data format

## What this build does

The opt-in capture is separate from the old Dump and Dump ALL settings. In the Chams tab, expand **Runtime capture**, choose **Start tracking**, close the menu and play. The on-screen **CHAMS TRACKING ACTIVE** indicator remains visible. F9 inserts a timestamped marker without consuming the key; it may still activate another F9 binding in the game/emulator. Use markers immediately before screenshots or actions. The menu also has **Add marker**. To finish, open the Chams tab and choose **Stop tracking**; wait for it to return. The stop operation waits for in-flight intercepted draws and the disk writer to drain. It can pause the UI, particularly with a slow or full disk.

The menu shows the session folder, elapsed seconds, data written, average data rate, frame and draw counts, record losses, incomplete ending frames and I/O error state. Copy the folder path with the button. A session can use **many gigabytes**: check free disk space first. Red **LOSS/ERROR** in the on-screen indicator means the trace has missing records or a writer failure. No configuration format or existing Chams control is changed. The capture is not automatically resumed on restart.

After stopping, upload **all** numbered `capture-NNNNNN.jsonl` parts and `summary.json`, alongside the screenshots and settings. Parts rotate at approximately 64 MiB, except a single record may extend past the target; capture parts may be compressed for upload. Screenshots are not recorded by the tracker. Do not upload other files from TEMP. If the process crashes or disk fills, `summary.json` or the last part may be missing or incomplete; still retain all produced parts for analysis. The program must be stopped before unloading the ReShade DLL. Abrupt termination can lose buffered records and cannot be called complete.

## How to read it

UTF-8 JSONL schema version `v=1`: each event has a session-local `seq`, `t_ns` monotonic offset, logical `thread`, context generation and context/surface frame ordinal. `session_start` contains the wall-clock Unix timestamp in milliseconds. `session_end` follows all admitted in-flight draws. Sequence gaps or `summary.dropped` indicate records were lost; `summary.io_error` and incomplete `frame_end` reasons indicate other problems. Start can occur inside an already running frame, so first frame records have `begin_reason=first_observed_unknown`. Surface IDs are session-local mappings of observed native device contexts, not persistent identities; handles can be reused and one window may have more than one device context.

`draw_begin` and `draw` have the same `draw_id`, context, surface and frame. Frame assignment is at intercepted call entry, even if a swap or context destruction occurs before the call returns. Each successful present advances only that context/surface stream. These ordinals represent **observed swap intervals**, not a guaranteed engine frame or a unique on-screen window. A failed present is retained and does not advance the frame. Context switches, creation, sharing and destruction are recorded where observed. Captures started after a context was created report `context_observed`, not a fabricated creation. Settings snapshots are emitted on start, menu setting changes and stop; key render settings are also recorded on draw records.

Draws include API name, counts where available, program and metadata epoch, GL buffer/VAO/framebuffer names, viewport, depth and blend state, scissor, cull, colour-write mask and the active texture-unit 2D binding, token/skin/wall hint bitsets, renderer/detection settings, and the actual Chams decision on its six wrapped calls. Nonwrapped calls are `not_evaluated`, not classifier rejections. Program-info, active-uniform and attached-shader events are associated by program ID, context and metadata epoch. Uniform name lengths over 255 bytes, program uniform counts over 4096, and attached-shader counts over 32 are explicitly reported as truncation/recordable-count limits. Only the active texture-unit 2D binding is recorded, not every texture target/unit or vertex attribute layout. Buffer-backed index and indirect offsets are recorded; client-memory addresses are not. Matrix/camera capture covers recognized Unity/HLSL names and records the available-location bitset; other uniforms or matrix conventions are not captured as values. Matrices and origins do not prove mesh ownership, pixel coverage or visible-object identity. GL numbers are context/session observations, not stable player or wall identifiers.

The passive diagnostic records only F9 marker transitions, rendering data and Chams settings. It does not capture shader source, texture/vertex contents, arbitrary process memory, browsing, passwords, unrelated files or screenshots. Program/uniform names and GL state are game rendering information. The output folder contains no GitHub credentials.

## Coverage and measurement limits

The current build instruments the 18 `glDraw*` / `glMultiDraw*` entry points implemented in `source/opengl/opengl.cpp`. It records calls even if Chams is disabled, rejected, or budget-limited. Other paths can bypass these interceptors, including unhooked vendor extensions, GLES/ANGLE paths not routed through these hooks, fixed-function `glDrawPixels`, driver-internal commands and GPU-generated work. No build can infer those events from silence. Indirect GPU command contents are not read back: an indirect or multi-draw record can have `count=-1`, and per-subdraw counts are not available. A nested record can appear when an addon expands an indirect command into direct commands; it is not necessarily additional game work.

The pre-existing Chams renderer shares settings, budget, overlay and own-tracker globals across rendering threads without comprehensive synchronization. The capture does not fix those races; its snapshots of those values may reflect concurrent changes, and the impact on real gameplay is unverified. The recorder's own queue and correlation state use synchronization, but that does not make the rest of the renderer thread-safe.

Program ID reuse is handled by a diagnostic metadata epoch invalidated on observed link/delete and context creation/destruction, but unobserved driver or share-group operations can bypass that tracking. `program_uniform` counts and shader record counts flag caps. Object identity and pixel-to-draw correlation remain unproven. Frame and context IDs are not game object IDs. Surface mapping may not correspond one-to-one to a window, especially after device-context reuse. A start, stop, destroyed context or abrupt exit can leave incomplete frame intervals. Check the summary and verifier instead of assuming completeness.

The writer uses a bounded asynchronous queue (32,768 records) and reports queue overflow, oversized records, allocation failures and I/O failures. It does not silently sample records, but a trace with loss is incomplete. Rendering threads still perform GL queries and metadata collection, construct records and acquire locks; a slow driver, heavy scene or full queue can reduce FPS. `instrumentation_ns` and `instrumentation_samples` are cumulative wall time inside selected draw-snapshot/serialization code; `enqueue_ns` is cumulative producer wait/work inside the recorder and can overlap the former. Neither is GPU time or a controlled FPS comparison. A Linux fake-GL test measured the capture path against disabled capture, but real BlueStacks/Windows GPU overhead has **not** been measured. First run should be short and monitor FPS, disk usage and the loss indicator before attempting long sessions.

`tools/chams_capture_verify.py SESSION_FOLDER` is a read-only offline validator for JSON syntax, sequence gaps, draw pairing, part counts and reported losses, and prints SHA-256 for each part. It cannot prove hooks saw all graphics activity or that an object is a player/wall. On untrusted uploads, validate all files and avoid following archive traversal links.
