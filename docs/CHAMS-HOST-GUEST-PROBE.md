# Host/guest renderer investigation: partial probe, not an identity bridge

## What is actually established

* The supplied ReShade logs show the Windows proxy `OPENGL32.dll` loaded into `HD-Player.exe` and hooks registered for the Windows system `opengl32.dll`. The recorder assigns session-local **thread 3 / native-context label 3** to 374,487 captured draws; the labels are not operating-system thread IDs. The older ReShade log is not proven to be the same session as capture 11. No host caller module or guest-process ID was recorded in capture 11.
* Read-only analysis of the hash-verified 2.132.1 **reference ARM64** ELF found a direct native control-path link: on its normal, non-patch branch, `COW.GamePlay.AvatarManager.SetUMARendererActive` loads its candidate `UMA.IUmaAvatar` field at `this+0x138`, makes virtual calls, and tail-calls the mapped `UMAData.SetUMARendererActive` method with the result and Boolean argument. This is static evidence connecting the gameplay avatar manager to UMA data on that path; the virtual target, live object type and patch behavior are not verified. That UMA method loads its renderer-like field and calls two Unity CoreModule wrappers. Token-table mapping and disassembly identify them as `UnityEngine.Component.get_gameObject` and `UnityEngine.GameObject.SetActive(Boolean)`. Their IL2CPP wrappers request corresponding icall names with signatures; in reference `libunity.so`, name-registration stubs pair the matching signature-less names with native code addresses. The resolver's live behavior has not been traced. These are enable/disable control paths, **not the actual rendering submission path**. No live code addresses or calls were verified.
* The same reference `libunity.so` has EGL imports and static code that opens `libGLESv2.so`, resolves `glDrawElements` through `dlsym`, and stores the resulting function pointer. That establishes a possible guest GLES entry path, not that this path ran for the captured draws. The DLL that decodes/translates the command, its thread, transport and internal process boundary remain unobserved. `HD-Player.exe` is the observed **host hook process**, not proof of the guest's address space or transport.
* Standard [`glDrawElements`](https://registry.khronos.org/OpenGL-Refpages/es2.0/xhtml/glDrawElements.xml) arguments do not contain a Unity renderer or owner. Thus the explicit semantic identity is not present **in that API call's arguments**. This does not prove it is absent from every buffer, extension, side channel, command transport or emulator-internal mapping. The actual point at which this installation may discard an internal association has not been observed.
* Public inventories for other BlueStacks releases list `libOpenglRender.dll` and `libGLES_V2_translator.dll` ([example](https://www.advanceduninstaller.com/BlueStacks-5-4252a24dcc56c05acdae3baf6e1abe54-application.htm)). They are search candidates, not proof those modules are loaded or execute on this user's installation. [AOSP's emulation design](https://raw.githubusercontent.com/android/platform_external_qemu/master/distrib/android-emugl/DESIGN) is an example architecture, not documentation of this BlueStacks build.

## Concrete alternative to investigate, not a correlation rule

The reference metadata includes `SkinnedMeshRenderer.GetVertexBuffer` / `GetVertexBufferImpl`, and the Unity native binary contains the corresponding icall string and registration stub. Unity documents a frame-dependent skinned vertex buffer, potentially alternating buffers during motion-vector rendering ([Unity documentation](https://docs.unity3d.com/ScriptReference/SkinnedMeshRenderer.GetVertexBuffer.html)). Unity separately documents `GraphicsBuffer.GetNativeBufferPtr` returning an OpenGL/ES buffer name ([documentation](https://docs.unity3d.com/2019.1/Documentation/ScriptReference/GraphicsBuffer.GetNativeBufferPtr.html)). The latter method was **not found in this reference's parsed method table**, and the installed Unity variant, availability, thread requirements, and actual value are unverified. Do not call it or infer a native name from an object pointer.

A promising alternative *if independently observed and validated* is a guest renderer-generation → guest buffer-generation mapping plus a verified guest-buffer → host-buffer translation mapping. Both relations must account for buffer replacement, batching, multiple streams, context/share groups, multiple render passes and object-name reuse. Equal guest and host numeric buffer names alone are not a proven bridge. Moreover, capture 11's `array_buffer` is the current `GL_ARRAY_BUFFER` binding; it is **not necessarily the buffer consumed by a VAO attribute**. `glVertexAttribPointer` records the then-bound buffer in VAO state, which may outlive later binding changes ([Khronos vertex specification](https://www.khronos.org/opengl/wiki/Vertex_Specification)). Existing captures do not include complete per-attribute VAO source mappings. Therefore even that alternative is not currently observable end to end.

The local-player → `Player` → `AvatarManager` → `GameObject` chain, the `UMAData` renderer and prop-owner fields are strong **static candidates** only. There is no measured mapping from them to a host draw, no verified per-owner instance generation, and no evidence that all body parts or preview/match instances share one renderer. No production ownership change follows from these findings.

## Quantified existing evidence

`tools/chams_bridge_coverage.py` audited every part of the supplied capture 11. It found 1,381,007 records, 384,303 paired and distinct host draw IDs, no sequence discontinuity, no reported drops, but an incomplete summary and three partial frames. All seven defined explicit guest identity/transport fields and host caller samples occurred **zero times**. That is not proof that no such signal exists inside BlueStacks; it means this capture cannot measure it.

The trace has 9,814 nonzero best-effort sync labels, of which 6,543 are observed in more than one context and on more than one recorded thread. These observations do **not** identify a guest renderer, prove command ordering across the emulator, GPU completion or one guest submission per host draw. Renderer creation, destruction, reuse and lifetime and guest-to-host asynchronous handoffs were not recorded; their counts are **unknown**, not zero. Completeness is bounded by intercepted APIs, capture start and incomplete final frames.

## Experimental host call-site probe

`source/chams_host_caller_probe.hpp` adds a deliberately narrower, opt-in **host-side call-site probe**, not a renderer bridge. It samples one in 512 eligible captured draws, at most 128 per capture session. Each `host_caller_sample` is linked by the recorder's `draw_id` to the same intercepted host draw call and carries the recorder's context/thread/sequence, sample ordinal, known module names and module-relative return addresses; it labels guest correlation `guest_unobserved`. It runs before addon handling and does not prove that the draw reached the driver, generated pixels, or belonged to the game. It emits neither arbitrary process memory nor full paths, unknown module names or absolute addresses. Unknown/unresolved modules remain unknown. Module labels are an allowlist and are not evidence a module is a translator; `opengl32.dll` could refer to different loaded files. A full stack may be truncated, and a returned address may identify a caller but not the original guest submission.

The probe is **compiled out by default**. Both a build definition `CHAMS_HOST_CALLER_PROBE` and environment value `CHAMS_HOST_CALLER_PROBE=1` set before process start are required; it then runs only during an active existing runtime capture. Sampling affects timing and may encounter loader/unwinder limitations. No guest injection, game modification, player label or classification change is included. This is not an instruction or request to perform a new capture: this prototype has not been validated on the user's BlueStacks installation and no additional capture is authorized here.

The synthetic tests cover disabled/enabled gating, bounded sampling, concurrent sequence allocation, session changes, no raw path/unknown module disclosure and draw-ID attachment. The Windows CI smoke test uses real stack/module APIs in a synthetic process, **not BlueStacks**. The default Windows Release build excludes the probe. A successful test or build would not establish a guest/host bridge, module role, full hook coverage, lifecycle correctness or in-game behavior.

## Independent global frame reset

The observed bug remains: `wglSwapBuffers` on presenting context 1 calls the global `begin_frame()`, and `touch_frame()` on drawing context 3 can run `reset_frame_caches()` with no current observation. Capture sequence 365757–365803 shows the unrelated present, estimate reset and changed decision for the same putative body draw. Context 3 has no observed present. Simply switching to a present-only per-context epoch could stop epoch advancement and preserve stale estimates; FBO clears are not established boundaries. Neither the host caller probe nor a future ownership mapping fixes that lifecycle problem.

## Remaining precise boundary

To turn the partial probe into a genuine bridge, the actual host draw caller and its corresponding guest graphics transport must first be identified, then an **explicit**, generation-safe identifier or validated translation-table entry must be observed at both ends. Buffer/name mapping is a candidate if its creation, replacement, translation and VAO consumption are observed; it is not currently proven. The supplied XAPK contains game libraries, not the installed BlueStacks guest graphics driver or its host translator binaries, and the supplied capture contains no caller stacks or guest events. Consequently their exact module/process handoff and identity-loss site cannot be determined from these materials. No time, order, distance or shader similarity is substituted for the missing causal evidence.
