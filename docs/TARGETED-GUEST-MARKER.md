# Targeted guest marker experiment

A separate ReShade add-on filters on current VirtualQuery metadata: committed MEM_PRIVATE regions whose protection equals PAGE_READWRITE | PAGE_NOCACHE. The selected regions are merely candidates, not proven guest RAM. It is a memory-content search, but only the owned 64-byte synthetic marker is searched; no raw host bytes are logged or saved. Other host process data may be read internally. Existing self-match exclusions, explicit controls, four 512 MiB separately gated batches and three gated candidate-only baseline/rotate/free comparisons carry over from CONTROLLED-GUEST-MARKER.md. Control filenames use `arena-target-marker-` to avoid collisions with other probes. A miss only covers successfully read selected regions within the bounded budget; ordinary private memory, mapped memory, other protections and the rest are not tested. Dynamic metadata and restarts mean a region snapshot or old cursor is not a mapping.

Only install/run after explicit user approval; restart is needed and performance/game enforcement risks apply. Do not change the renderer DLL or security settings. Each scan batch requires explicit approval. A positive candidate is not a general translation, nor an ARM64 game address. If no candidate is found, stop/clean the guest. If found, perform baseline, fresh-marker rotation, and unmap comparisons before interpreting it; copies can still mislead.

Tests: production filter predicate is tested with synthetic Windows MEMORY_BASIC_INFORMATION cases; a real PAGE_READWRITE allocation is checked to produce zero reads under the target filter. The mock host uses MARKER_TEST to disable the production filter for its ordinary PAGE_READWRITE fixture and restrict scanning to that fixture; it tests gating/candidate/rotation/free, not BlueStacks or PAGE_NOCACHE-backed memory. Windows release compilation always enables the target filter.
