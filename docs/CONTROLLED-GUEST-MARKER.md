# Controlled guest-to-host marker experiment

## Purpose and limits

Test whether bytes from a **cooperating guest-owned process** can be observed in the currently hooked Windows host process. This does not read or inject into the game, does not prove an arbitrary guest-virtual-to-host translation, and does not read player lists. Secure Boot, kernel drivers and the renderer DLL are untouched. The user must explicitly authorize running the test and each bounded scanning batch. Scan activity may affect performance or trigger game enforcement.

`GuestMarker-arm64` is a standalone Android native executable. It allocates a 4096-byte anonymous page, writes 64 random bytes and prints a diagnostic line with its PID, its own guest virtual address, version, and the synthetic marker (hex). A controlled `.rotate` flag changes the bytes in the same page; a `.stop` flag zeros and unmaps the page. The program automatically stops and unmaps after 900 seconds. It never opens another process. Paths are scoped to a validated alphanumeric session in `/data/local/tmp` and the process should be cleaned up with its own stop control. This executable is not installed in the game.

`ControlledMarkerProbe.addon64` is a separate ReShade add-on in the HD-Player host. It scans only its own process, up to four separately triggered batches of 8 x 64 MiB attempted each (maximum 2 GiB per add-on load), 10 seconds per slice, 4 ms pause per 64 KiB, 2 seconds between slices. It only begins after a trigger; no automatic batches. It retains the cursor only during that process lifetime. The first trigger contains the 128 ASCII hex characters of the synthetic marker; controller must write it to a temporary file and atomically rename it to the trigger so the worker never sees a partially written control. Later batch triggers may be empty. It emits counts, cursor and a candidate address, but never emits copied host bytes. It stops searching on a match, cancellation, allocation failure, stall or full range.

**Self-match protection:** the scanner excludes its own marker's allocation (the worker's stack allocation), its temporary scan-buffer allocation, and the add-on module. This reduces false self-matches but does not rule out other process/OS cached copies. A hit is merely a host candidate. Starting from the captured first candidate only, up to three separately triggered fixed-length reads report Boolean equality against the initial marker and a supplied expected marker; no raw host bytes are emitted and no arbitrary address is accepted. Baseline, guest rotation and guest unmap observations can distinguish some stale copies, but even synchronized changes do not prove a general mapping, address translation or access to the game. A miss is inconclusive due to scan bounds, unobserved processes, memory changes, and emulator representations.

Controls: `arena-marker-ready-<pid>-<token>-<batch>.txt`, `arena-marker-trigger-<pid>-<token>-<batch>.flag` and `arena-marker-result-<pid>-<token>-<batch>.txt`; verification uses `arena-marker-verify-{ready,trigger,result}-<pid>-<token>-<stage>...`. PID/nonce ready files can be stale after unload. Confirm the active instance from the current PID and log; verify prior batch completion/cursor before another trigger. Do not continue a cursor after restart. Trigger and result files are new-only.

Tests: a native Linux synthetic guest lifecycle test, a Windows marker parser and boundary/self-exclusion scanner test, and a Windows mock host that verifies explicit trigger, first-candidate provenance, synthetic mutation and free comparisons. Windows mock scanner has a test-only target range and reduced budgets; those compile-time paths are absent from the production add-on. The Android artifact is cross-compiled for ARM64 Android 8+ with GitHub Actions NDK. Tests do not recreate BlueStacks memory architecture.
